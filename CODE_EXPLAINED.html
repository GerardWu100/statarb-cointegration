Reading the cointegration study

What the code does, how its four modules connect, where its numbers come from, and which biases remain.

How to use this

Sections follow execution order, from settings to printed metrics. Each code snippet is copied from src/statarb_cointegration/. Each number in a sample box comes from running uv run statarb-pipeline on this repository's frozen Parquet file on 10 August 2026; none was estimated. The process in plain English

The code asks whether Coca-Cola (KO) and Pepsi (PEP) prices move apart and then return together reliably enough to trade. It fits a straight line from PEP price to KO price over twenty years, measures the gap between the actual KO price and that line, and tests whether the gap returns to its average. The test fails: its p-value is 0.2255 against a 0.05 threshold. The code still runs the trade, including costs and daily accounting, to measure the result of ignoring that failure: a 46.2 percent loss over two years.

01Project scope and file layout

Two terms explain the rest of the page.

Cointegration means two price series can wander, while a fixed combination of them returns to a stable level. If KO and PEP were cointegrated, the gap between KO and a fixed multiple of PEP would keep returning to its average. That is the behaviour this strategy tries to trade.

Stationary means a series has a stable average and spread, so a large distance from the average today contains information about tomorrow. A series with a unit root has no such anchor and can keep wandering.

The project fits the combination, tests the gap for stationarity, then runs the trade as a historical simulation. This measures the cost of ignoring a failed test.

Why the logic lives in one module

All financial logic is in research.py. pipeline.py selects the training slice and writes files; cli.py prints. This separation lets the four unit tests import run_backtest directly and pass it a hand-built, twenty-row price frame without a configuration file, Parquet data, or disk writes.

02Configuration — config.toml, ResearchConfig, load_config

def load_config(path: Path | None = None) -> ResearchConfig:
    """Load the single project configuration file."""

    project_root = Path(__file__).resolve().parents[2]
    config_path = path or project_root / "config.toml"
    with config_path.open("rb") as stream:
        values = tomllib.load(stream)["research"]
    return ResearchConfig(project_root=project_root, **values)
In plain words

Read the settings, check that they work together, and locate the data and output folders from the code's location rather than from the terminal's current folder.

What it does

Input: an optional path to a TOML (Tom's Obvious, Minimal Language) file; no path means the repository's config.toml. Output: a ResearchConfig with fifteen settings and two derived paths. Role: every other function receives this object instead of reading its own files or constants.

Each setting and the change it controls:

SettingValueWhat changes if you move it

backtest_start2023-10-11First day the strategy may trade and the boundary the fit cannot cross. Moving it changes both training and test data.
backtest_end2025-09-30Last trading day. Any open position is closed on this date.

Trap: the settings are checked against each other, not just individually

__post_init__ rejects configurations that fail 0 <= exit_z < entry_z < stop_z or have a training window no longer than the rolling window. Without the first check, a position could open and close on the same day, paying two trading costs. The error appears when settings load, not hundreds of lines later.

Why paths are derived from the file, not the terminal

Path(__file__).resolve().parents[2] walks from src/statarb_cointegration/config.py to the repository root. The Parquet path and output folder are built from that root. The pipeline therefore behaves the same from the project root, another directory, or a scheduler.

One setting that is not in the settings file

The Parquet filename ko_pep_combined_adj_close_price.parquet is written in config.py, not config.toml. Using another pair requires a Python edit. That is a deliberate simplification for this two-ticker study, but it is the one tunable value outside the settings file.

04The relation and the test — fit_cointegration

x = training_prices["PEP"].to_numpy()
y = training_prices["KO"].to_numpy()
beta, alpha = np.polyfit(x, y, 1)
fitted = alpha + beta * x
residual = y - fitted
residual_ss = float(np.square(residual).sum())
total_ss = float(np.square(y - y.mean()).sum())
adf_statistic, adf_pvalue, *_ = adfuller(residual, regression="c", autolag="AIC")
eg_statistic, eg_pvalue, _ = coint(y, x, trend="c", autolag="aic")
In plain words

Fit the best straight line from PEP price to KO price, measure each day's distance from the line, and run two tests to see whether those distances return to zero or keep wandering.

What it does

Input: a price frame covering only the training window. Output: a CointegrationFit holding eight numbers: intercept, slope, fit quality, and two test statistics with their p-values. Role: the slope becomes the hedge ratio—the number of PEP shares used per KO share. The intercept and slope define the traded gap, and the Engle-Granger p-value is the research gate.

The formula — the line and the hedge ratio

$$\hat\beta=\frac{\sum_{t=1}^{T}(x_t-\bar x)(y_t-\bar y)}{\sum_{t=1}^{T}(x_t-\bar x)^2}, \qquad \hat\alpha=\bar y-\hat\beta\,\bar x, \qquad e_t=y_t-\hat\alpha-\hat\beta x_t$$

$y_t$ is the KO adjusted close on day $t$ in US dollars; $x_t$ is the PEP adjusted close. $T=5000$ is the number of training days. $\bar y$ and $\bar x$ are their averages. $\hat\beta$ is the slope and hedge ratio: the number of PEP shares to sell per KO share owned. $\hat\alpha$ is the intercept in US dollars. $e_t$ is the residual, the gap between the actual KO price and the line's prediction. np.polyfit(x, y, 1) computes these values and returns the slope before the intercept, so the code unpacks them as beta, alpha.

The formula — how well the line fits

$$R^2=1-\frac{\sum_{t=1}^{T}e_t^2}{\sum_{t=1}^{T}(y_t-\bar y)^2}$$

The share of KO price movement explained by PEP price. One means the line passes through every point; zero means it is no better than the flat average. The code writes this as 1.0 - residual_ss / total_ss.

The formula — the two stationarity tests

The Augmented Dickey-Fuller (ADF) regression, which adfuller(residual, regression="c", autolag="AIC") runs on the residual series:

$$\Delta e_t=c+\gamma\,e_{t-1}+\sum_{i=1}^{k}\phi_i\,\Delta e_{t-i}+u_t, \qquad H_0:\gamma=0$$

$\Delta e_t=e_t-e_{t-1}$ is the one-day change in the gap. $c$ is a constant. $\gamma$ measures the pull back: if $\gamma$ is reliably below zero, a large gap tends to shrink, which is what stationary means here. The $\phi_i$ terms capture short-term movement in the changes. $k$ is chosen by the Akaike Information Criterion, a rule that balances extra terms against fit. $u_t$ is leftover noise. The null hypothesis $H_0$ is $\gamma=0$, meaning there is no pull back. A small p-value rejects it.

The Engle-Granger test, coint(y, x, trend="c", autolag="aic"), runs the same regression but uses critical values that account for estimating $\hat\alpha$ and $\hat\beta$ from the same data. That is why its p-value is much larger than the plain ADF result on the same numbers.

The test statistics are nearly equal, -2.6295 and -2.6307, but the p-values are 0.087 and 0.225. The data did not change; the critical-value table did. The Engle-Granger p-value, 0.2255, is above 0.05, so cointegration_passed is 0.

Trap: a high R-squared is not evidence of cointegration

A high R-squared does not prove cointegration. The line explains 96.0 percent of KO price variation, but that result means little on its own. Two series that both rise over twenty years can fit each other well by construction; this is called a spurious regression. The key question is whether the leftover gap returns, and the correct test says it does not.

Why both tests are reported when only one counts

A less careful version might quote the plain ADF p-value of 0.087; at a 10 percent threshold it would nearly pass. Showing it beside the correct value, 0.225, makes the correction visible. The docstring identifies the Engle-Granger value as the gate and the ADF value as a diagnostic.

The fit is a single fixed line, and it is never refreshed

fit_cointegration runs once on data ending 2023-10-10. The resulting $\hat\alpha$ and $\hat\beta$ stay fixed for all 494 backtest days. Refitting inside the test window would leak information, but a relationship that changed during 2024 would leave the strategy trading an outdated gap. The blog/generate_charts.py diagnostic shows that drift.

05The signal — compute_causal_signal

residual = prices["KO"] - fit.alpha_usd - fit.beta * prices["PEP"]
lagged = residual.shift(1)
rolling_mean = lagged.rolling(rolling_window).mean()
rolling_std = lagged.rolling(rolling_window).std(ddof=1)
return pd.DataFrame(
    {
        "residual_usd": residual,
        "rolling_mean_usd": rolling_mean,
        "rolling_std_usd": rolling_std,
        "z_score": (residual - rolling_mean) / rolling_std,
    },
    index=prices.index,
)
In plain words

Measure today's gap from the line, then compare it with the previous sixty gaps. The previous window ends yesterday, so today's gap never helps judge itself.

What it does

Input: the full price history, the fixed fit, and the window length. Output: a four-column frame with the same index as the prices: the gap, its trailing average, its trailing spread, and its score. Role: the trading rule uses only z_score.

The formula — the score, exactly as the code builds it

$$\mu_{t-1}=\frac{1}{L}\sum_{i=1}^{L}e_{t-i}, \qquad \sigma_{t-1}=\sqrt{\frac{1}{L-1}\sum_{i=1}^{L}\bigl(e_{t-i}-\mu_{t-1}\bigr)^2}, \qquad z_t=\frac{e_t-\mu_{t-1}}{\sigma_{t-1}}$$

$e_t$ is today's gap in US dollars. $L=60$ is rolling_window. The sums start at $i=1$, not $i=0$, so the window runs from $e_{t-60}$ through $e_{t-1}$ and excludes today. The $L-1$ divisor gives the sample standard deviation; ddof=1 selects it, where ddof means delta degrees of freedom. $z_t$ has no units: it says how many trailing standard deviations today's gap is from the trailing average.

One row checked by hand. On 2023-10-12, the gap is $e_t = 49.0459 - 4.573179 - 0.334505 \times 144.8800 = -3.9904$ US dollars. The 60-day window behind it runs from 2023-07-19 to 2023-10-11 inclusive, contains 60 values, and has average $-4.526974$ and spread $0.750488$. So $z_t = (-3.9904 - (-4.526974)) / 0.750488 = 0.71493$, which matches the 0.7149 the code reports. The window was printed separately and confirmed not to contain 2023-10-12 itself.

Why the shift comes before the rolling, not after

The two orders look similar, but only one is correct. The code writes residual.shift(1).rolling(60).mean(): shift first, then average. This averages days $t-60$ through $t-1$. Writing residual.rolling(60).mean().shift(1) would use days $t-61$ through $t-2$, one day too early. Writing residual.rolling(60).mean() would include today and pull today's benchmark toward today's gap, shrinking every score.

Trap: the rolling window happily crosses the training boundary

On the first backtest day, the sixty-day window is almost all training data, where the fitted gaps average zero by construction. This is not look-ahead: every day is in the past. But the first few weeks of scores are measured against a period used to fit the regression, so they may look better behaved than they would in live trading.

The test that guards this

test_signal_does_not_use_current_or_future_residuals builds a twelve-day price frame, computes the signal, adds 1,000 US dollars to the last KO price, and computes it again. Every score except the last must stay unchanged, as must the last day's rolling average. If shift(1) were removed, this test would fail.

06Position sizing — _target_holdings

target_gross = config.initial_capital_usd * config.gross_exposure_multiple
ko_units = target_gross / (ko_price + abs(beta) * pep_price)
return side * ko_units, -side * beta * ko_units
In plain words

Choose the number of KO shares so both legs reach the target position size, then set the PEP shares from the fitted slope.

What it does

Input: today's two prices, the slope, a direction of +1 or -1, and the config. Output: two signed share counts. Role: called once for each entry in the backtest loop; nothing else calls it.

The formula — the sizing

$$q_t=\frac{C\cdot G}{P^{KO}_t+\lvert\hat\beta\rvert\,P^{PEP}_t}, \qquad n^{KO}_t=s_t\,q_t, \qquad n^{PEP}_t=-s_t\,\hat\beta\,q_t$$

$C$ is initial_capital_usd, 100,000 US dollars. $G$ is gross_exposure_multiple, 2.0. $P^{KO}_t$ and $P^{PEP}_t$ are the two closing prices on the entry day. $\hat\beta$ is the fitted slope. $s_t$ is the direction: $+1$ bets the gap widens, and $-1$ bets it narrows. $q_t$ is a positive share count. $n^{KO}_t$ and $n^{PEP}_t$ are signed holdings: positive means owned and negative means shorted.

The denominator makes the total position size exactly the target:

$$\lvert n^{KO}_t\rvert P^{KO}_t+\lvert n^{PEP}_t\rvert P^{PEP}_t =q_t\bigl(P^{KO}_t+\lvert\hat\beta\rvert P^{PEP}_t\bigr)=C\cdot G$$

Sample data
in — first real entry, 2023-10-19 
ko_price   50.476109

side              -1    (z = +1.5163)
capital  100000.0 x 2.0

                     total = 200000.0000  <- exactly C x G

The score was +1.5163, so the gap was unusually wide. The code bet on it narrowing: side = -1, short KO, and buy PEP.

Why the absolute value appears in one place and not the other

The denominator uses abs(beta) because it adds position sizes, which are always positive. The PEP share count keeps the signed beta: with a negative slope, the correct hedge would own both legs rather than short one. The fitted slope is +0.3345, but the code also handles a negative slope.

This position is hedged on the relationship, not on dollars

At the first entry, the KO leg is 101,256 US dollars and the PEP leg is 98,744 US dollars. That near balance is accidental. A slope of 0.3345 and a PEP price about three times the KO price make the legs similar in value. If that price ratio changed, the position would gain net market exposure and the code would not detect it.

07The backtest loop — run_backtest

This is the project's most involved function. It processes the 494 backtest days one at a time and carries five pieces of state: two share counts, the direction, the entry date, and running trade totals. Each day follows the same order.

flowchart TD A["mark prior holdings to today prices"] --> B["accrue borrow and financing on prior values"] B --> C["read today z-score"] C --> D{"holding a position"} D -->|yes| E{"z at the exit band, past the stop, or last day"} D -->|no| F{"z inside the entry band and not the last day"} E -->|yes| G["set both share counts to zero"] E -->|no| H["hold unchanged"] F -->|yes| I["size a new position at today's close"] F -->|no| H G --> J["charge cost on the change in holdings"] H --> J I --> J J --> K["update equity, record the row"]

Diamonds are decisions; boxes are actions. The order matters: profit and loss is settled before the signal is read, so a decision today cannot earn today's price move.

Step one — value yesterday's position at today's prices

if previous_prices is not None:
    gross_pnl = ko_shares * (
        float(current_prices["KO"]) - float(previous_prices["KO"])
    ) + pep_shares * (
        float(current_prices["PEP"]) - float(previous_prices["PEP"])
    )
The formula — daily profit and loss

$$\Pi_t=n^{KO}_{t-1}\bigl(P^{KO}_t-P^{KO}_{t-1}\bigr) +n^{PEP}_{t-1}\bigl(P^{PEP}_t-P^{PEP}_{t-1}\bigr)$$

$\Pi_t$ is the day's gross profit or loss in US dollars, before costs. $n^{KO}_{t-1}$ and $n^{PEP}_{t-1}$ are the share counts set at yesterday's close. They are still the current holdings here because the loop has not changed them. $P^{KO}_t$ and $P^{PEP}_t$ are today's closes. Holdings use $t-1$ while prices use $t$; that is the backtest's timing rule.

Step two — charge the costs of holding the position

short_value = max(-ko_shares * float(previous_prices["KO"]), 0.0) + max(
    -pep_shares * float(previous_prices["PEP"]), 0.0
)
long_value = max(ko_shares * float(previous_prices["KO"]), 0.0) + max(
    pep_shares * float(previous_prices["PEP"]), 0.0
)
borrow_cost = short_value * config.short_borrow_rate_annual * daily_rate
financing_cost = long_value * config.financing_rate_annual * daily_rate
The formula — borrow, financing, and trading cost

$$B_t=\frac{r_b}{D}\Bigl[\max\bigl(-n^{KO}_{t-1}P^{KO}_{t-1},\,0\bigr) +\max\bigl(-n^{PEP}_{t-1}P^{PEP}_{t-1},\,0\bigr)\Bigr]$$

$$F_t=\frac{r_f}{D}\Bigl[\max\bigl(n^{KO}_{t-1}P^{KO}_{t-1},\,0\bigr) +\max\bigl(n^{PEP}_{t-1}P^{PEP}_{t-1},\,0\bigr)\Bigr]$$

$$K_t=\frac{c}{10^4}\Bigl[\bigl\lvert n^{KO}_t-n^{KO}_{t-1}\bigr\rvert P^{KO}_t +\bigl\lvert n^{PEP}_t-n^{PEP}_{t-1}\bigr\rvert P^{PEP}_t\Bigr]$$

$B_t$ is the short borrow fee, $F_t$ the long financing charge, and $K_t$ the trading cost, all in US dollars for day $t$. $r_b=0.01$ and $r_f=0.05$ are annual rates. $D=252$ is trading_days_per_year; dividing by it gives one trading day's share. $c=5$ is transaction_cost_bps, and $10^4$ converts basis points to a fraction. The max terms separate short and owned amounts, so each leg pays the applicable rate. $B_t$ and $F_t$ use yesterday's prices and holdings; $K_t$ uses today's prices and today's change in holdings.

The formula — the account

$$E_t=E_{t-1}+\Pi_t-B_t-F_t-K_t,\qquad E_0=C$$

$E_t$ is the account value in US dollars at the close of day $t$, and $C$ is starting capital. The code revalues open positions daily, so a loss appears in drawdown while the trade is open, not only when it closes.

Step three — apply the entry and exit rule

is_last_date = row_number == len(sample) - 1
if side != 0 and (
    abs(z_score) <= config.exit_z
    or abs(z_score) >= config.stop_z
    or is_last_date
):
    exit_reason = (
        "end of sample"
        if is_last_date
        else "mean reversion"
        if abs(z_score) <= config.exit_z
        else "stop loss"
    )
    ko_shares = 0.0
    pep_shares = 0.0
elif (
    side == 0
    and config.entry_z <= abs(z_score) < config.stop_z
    and not is_last_date
):
    side = -1 if z_score > 0.0 else 1
The formula — the rule, as written

Open a position when flat:

$$s_t=-\operatorname{sign}(z_t) \quad\text{if}\quad s_{t-1}=0 \;\text{ and }\; z_{\text{entry}}\le\lvert z_t\rvert<z_{\text{stop}} \;\text{ and }\; t\ne T_{\text{end}}$$

Close a position when holding one:

$$s_t=0 \quad\text{if}\quad s_{t-1}\ne 0 \;\text{ and }\;\bigl(\lvert z_t\rvert\le z_{\text{exit}} \;\text{ or }\;\lvert z_t\rvert\ge z_{\text{stop}} \;\text{ or }\; t=T_{\text{end}}\bigr)$$

$s_t$ is the direction held after day $t$: $+1$, $-1$, or $0$ for flat. $z_t$ is the score. $z_{\text{entry}}=1.5$, $z_{\text{exit}}=0.2$, and $z_{\text{stop}}=2.5$ are the configured thresholds. $T_{\text{end}}$ is the last backtest date. $\operatorname{sign}(z_t)$ is $+1$ when $z_t$ is positive; the minus sign bets that a wide gap will narrow.

Why the entry band has an upper edge as well as a lower one

The condition is $1.5\le\lvert z_t\rvert<2.5$, not just $\lvert z_t\rvert\ge 1.5$. A gap beyond the stop would otherwise be entered and stopped out the next day, paying two trading costs for nothing. The value 2.5 is both the risk stop and the edge of the entry band.

Why the last day is treated specially in both branches

is_last_date closes any open position, so reported profit and loss covers every position and no value is left out. It also blocks a new entry: a position opened on the final close would open and close at once while paying twice.

08The summary numbers — the metrics dictionary

returns = daily["net_pnl_usd"] / daily["equity_usd"].shift(1).fillna(
    config.initial_capital_usd
)

drawdown = daily["equity_usd"] / running_peak - 1.0
return_std = float(returns.std(ddof=1))
sharpe = (
    float(returns.mean() / return_std * np.sqrt(config.trading_days_per_year))
    if return_std
    else np.nan
)
The formula — return, Sharpe ratio, drawdown

$$r_t=\frac{\Pi_t-B_t-F_t-K_t}{E_{t-1}}, \qquad S=\frac{\bar r}{s_r}\sqrt{D}, \qquad DD_t=\frac{E_t}{\max\bigl(C,\;\max_{u\le t}E_u\bigr)}-1$$

$r_t$ is the day's return as a fraction of yesterday's account value; on the first day, the denominator is starting capital $C$. $\bar r$ is average daily return and $s_r$ its sample standard deviation across 494 days. $\sqrt{D}$ with $D=252$ converts a daily figure to a yearly one because independent daily returns grow in variance, so their spread grows with the square root of the number of days. $S$ is the Sharpe ratio, average return divided by its spread. It uses no risk-free rate, so the funding charge inside $F_t$ takes that place. $DD_t$ is the drawdown from the highest account value so far. Starting capital counts as the first peak, so a strategy that never gains still shows its full loss.

Why the peak is clipped at the starting capital

cummax().clip(lower=initial_capital) counts day zero as a peak. Without the clip, an account that fell on day one and never recovered would measure drawdown from that lower value and understate the loss. Here the reported maximum drawdown of 47.3 percent uses the full 100,000 US dollars.

The Sharpe ratio here is a description, not a decision tool

With 494 daily observations and one strategy, a Sharpe ratio of -1.77 describes persistent losses rather than one bad week. It says nothing about a future period. The study also failed its statistical gate, so this number should not rank anything.

In plain words

Take prices strictly before the backtest, keep the latest five thousand, fit the line only on them, then run the strategy on the full history so the rolling window has enough earlier data.

Why this is where look-ahead would have crept in, and does not

These four lines separate model information from test information. prices.index < config.backtest_start is strict, so 2023-10-11 is excluded from training. .tail(5000) then selects the latest 5,000 rows, ending 2023-10-10. The resulting fit is passed to run_backtest and never recomputed. run_backtest receives the full price history because the first backtest day needs sixty earlier days for its rolling window. Those days are all in the past.

Trap: the length check turns silent truncation into an error

.tail(5000) on a shorter history returns whatever exists without complaint. The strategy could then fit on 800 days while the config still says 5,000. The equality check catches that mismatch at the pipeline boundary.

The three ways to run it

Installed command: uv run statarb-pipeline, declared in pyproject.toml as statarb_cointegration.cli:main. Script: uv run python scripts/run_pipeline.py, which imports the same main. Library: from statarb_cointegration.pipeline import run_pipeline, which notebooks/demo.ipynb calls in one cell. All three accept an optional --config path and write the same three CSV files.

What lands on disk

outputs/tables/daily_backtest.csv: 494 rows and 12 columns of daily state. outputs/tables/trades.csv: 13 completed trades. outputs/tables/summary.csv: 16 metric rows written with an f-string rather than through pandas. The entire outputs/ folder is in .gitignore, so the pipeline does not modify the repository.

16Honest limitations

The pair and the split date were chosen with the whole history visible

This is a structural bias the code cannot fix. A person who could see prices through 2025 selected KO and PEP, the 5,000-day window, and the 2023-10-11 split. The pipeline cannot undo those choices. The result is unfavourable—a failed test and a 46.2 percent loss—but that does not remove the bias. If this design were reused on a pair that did pass, the same choices would make that result less convincing. The proper out-of-sample fix is to choose the pair and window in one period, then test them in a period not yet viewed.

One pair, one window, one strategy — no statistical power either way

Thirteen trades over 494 days cannot support a claim about expected return. The Sharpe ratio of -1.77 and win rate of 0.31 describe this sample; they do not estimate future results. The Engle-Granger p-value of 0.2255, computed from 5,000 observations, is the study's main statistical result, and it does not support the premise.

Adjusted closes are not tradeable prices

Every Parquet price is a close adjusted for splits and dividends. The data has no bid, ask, order size, or intraday path. The 5 basis point trading cost stands in for a spread that is not recorded. Market impact, KO borrow availability, dividends owed on the short leg, and broker-specific margin terms are also absent.

Entry is priced at the close that produced the signal

The score and entry price use the same close. A real trader would submit a market-on-close order before seeing that close or trade at the next open. The profit-and-loss timing is right, but each of the thirteen entries and exits has an optimistic fill by roughly one day of noise.

The position is sized once and never rebalanced

Share counts are fixed at entry and held until exit. During trade 10's 118 calendar days, price changes moved the position away from 200,000 US dollars and moved its dollar hedge away from 0.3345. A live implementation would rebalance, pay for it, and produce a different result.

The relationship is fitted once and assumed to hold for two years

The slope uses data ending October 2023 and stays unchanged through September 2025. blog/generate_charts.py partly shows that the slope was not stable across periods. Refitting inside the test window would be look-ahead, so the code correctly avoids it. The trade-off is that the strategy knowingly uses a relationship that has already moved.
