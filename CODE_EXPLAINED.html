Reading the cointegration study

What the code does, how the four modules fit together, where every number comes from, and the biases the design cannot remove.

How to use this

Sections follow execution order, from configuration to printed metrics. Every code snippet is copied from the files under src/statarb_cointegration/. Every number in a sample box was produced by running uv run statarb-pipeline on the frozen parquet file in this repository on 10 August 2026, not estimated. Coloured boxes carry the design choices, the traps, and the honest limits.

The process in plain English

The code asks one question: do Coca-Cola (KO) and Pepsi (PEP) share prices drift apart and then come back together reliably enough to trade? It fits a straight line of KO price against PEP price on twenty years of history, takes the gap between the real KO price and the line, and tests whether that gap is the kind of series that returns to its own average. The test says no, with a p-value of 0.2255 against a 0.05 threshold. The code then runs the trade anyway, with costs and daily accounting, to measure what ignoring that answer would have cost: a 46.2 percent loss over two years.

01What the project is and where the files live

Two terms first, because everything below rests on them.

Cointegration means two price series each wander without settling anywhere, but some fixed combination of them does settle around a constant level. If KO and PEP were cointegrated, the gap between the KO price and a fixed multiple of the PEP price would keep returning to its average, and you could trade that return.

Stationary means a series has a stable average and a stable spread, so that being far from the average today tells you something about tomorrow. A series with a unit root is the opposite: it wanders with no anchor, so being far from yesterday's average tells you nothing.

The project fits the combination, tests the gap for stationarity, and then runs the trade as a controlled failure so the cost of ignoring a failed test is measurable rather than hypothetical.

Why the logic lives in one module

All the finance is in research.py. pipeline.py only chooses the training slice and writes files; cli.py only prints. That split is what makes the four unit tests possible: they import run_backtest directly and hand it a twenty-row hand-built price frame, with no configuration file, no parquet, and no disk writes.

02Configuration — config.toml, ResearchConfig, load_config

def load_config(path: Path | None = None) -> ResearchConfig:
    """Load the single project configuration file."""

    project_root = Path(__file__).resolve().parents[2]
    config_path = path or project_root / "config.toml"
    with config_path.open("rb") as stream:
        values = tomllib.load(stream)["research"]
    return ResearchConfig(project_root=project_root, **values)
In plain words

Read the settings file, check the settings make sense together, and work out where the data and output folders are relative to the code rather than relative to wherever you happen to be standing in the terminal.

What it does

Input: an optional path to a TOML file; nothing means the repository's own config.toml. Output: a frozen ResearchConfig with fifteen settings plus two derived paths. Role: every other function takes this object rather than reading files or constants of its own.

The whole settings surface, and what moving each one actually changes:

SettingValueWhat changes if you move it

Trap: the settings are checked against each other, not just individually

__post_init__ rejects a configuration where 0 <= exit_z < entry_z < stop_z fails, and one where the training window is not longer than the rolling window. Without the first check you could set an exit threshold above the entry threshold, and every position would close on the same day it opened while still paying two lots of trading cost. The error arrives at load time instead of as a strange result three hundred lines later.

Why paths are derived from the file, not the terminal

Path(__file__).resolve().parents[2] walks up from src/statarb_cointegration/config.py to the repository root. The parquet path and the outputs folder hang off that. The pipeline therefore produces the same result whether you run it from the project root, from your home directory, or from a scheduler.

One setting that is not in the settings file

The parquet filename ko_pep_combined_adj_close_price.parquet is written into config.py, not into config.toml. Pointing the study at a different pair means editing Python. It is a deliberate simplification for a two-ticker study, but it is the one tunable value that escaped the configuration file.

04The relation and the test — fit_cointegration

x = training_prices["PEP"].to_numpy()
y = training_prices["KO"].to_numpy()
beta, alpha = np.polyfit(x, y, 1)
fitted = alpha + beta * x
residual = y - fitted
residual_ss = float(np.square(residual).sum())
total_ss = float(np.square(y - y.mean()).sum())
adf_statistic, adf_pvalue, *_ = adfuller(residual, regression="c", autolag="AIC")
eg_statistic, eg_pvalue, _ = coint(y, x, trend="c", autolag="aic")
In plain words

Draw the best straight line through KO price plotted against PEP price, measure how far each day sits from that line, and run two statistical tests asking whether those distances return to zero or just wander.

What it does

Input: a price frame covering only the training window. Output: a frozen CointegrationFit holding eight numbers: intercept, slope, fit quality, and two test statistics with their p-values. Role: the slope becomes the hedge ratio, the intercept and slope define the gap that is traded, and the Engle-Granger p-value is the research gate.

The formula — the line and the hedge ratio

$$\hat\beta=\frac{\sum_{t=1}^{T}(x_t-\bar x)(y_t-\bar y)}{\sum_{t=1}^{T}(x_t-\bar x)^2}, \qquad \hat\alpha=\bar y-\hat\beta\,\bar x, \qquad e_t=y_t-\hat\alpha-\hat\beta x_t$$

$y_t$ is the KO adjusted close on day $t$ in US dollars, $x_t$ the PEP adjusted close. $T=5000$ is the number of training days. $\bar y$ and $\bar x$ are their averages over those days. $\hat\beta$ is the slope, which doubles as the hedge ratio: the number of PEP shares to sell per KO share owned. $\hat\alpha$ is the intercept in US dollars. $e_t$ is the residual, the gap in US dollars between the actual KO price and the price the line predicts. This is exactly what np.polyfit(x, y, 1) computes; note it returns the slope first and the intercept second, which is why the code unpacks it as beta, alpha.

The formula — how well the line fits

$$R^2=1-\frac{\sum_{t=1}^{T}e_t^2}{\sum_{t=1}^{T}(y_t-\bar y)^2}$$

The fraction of the up-and-down movement in the KO price that the PEP price explains. One means the line passes through every point; zero means the line is no better than the flat average. The code writes this literally as 1.0 - residual_ss / total_ss.

The formula — the two stationarity tests

The Augmented Dickey-Fuller regression, which adfuller(residual, regression="c", autolag="AIC") runs on the residual series:

$$\Delta e_t=c+\gamma\,e_{t-1}+\sum_{i=1}^{k}\phi_i\,\Delta e_{t-i}+u_t, \qquad H_0:\gamma=0$$

$\Delta e_t=e_t-e_{t-1}$ is the one-day change in the gap. $c$ is a constant. $\gamma$ is the pull-back coefficient: if $\gamma$ is reliably below zero, a large gap tends to shrink, which is what stationary means here. The $\phi_i$ terms mop up short-run momentum in the changes, and $k$ is chosen automatically by the Akaike Information Criterion, a rule that trades extra terms against better fit. $u_t$ is the leftover noise. The null hypothesis $H_0$ is $\gamma=0$, meaning no pull-back at all. A small p-value rejects it.

The Engle-Granger test, coint(y, x, trend="c", autolag="aic"), runs the same regression but scores it against critical values that already allow for $\hat\alpha$ and $\hat\beta$ having been estimated from the same data. That correction is why its p-value is much larger than the plain Dickey-Frank result on identical numbers.

The two test statistics are almost the same number, -2.6295 against -2.6307, but their p-values are 0.087 and 0.225. Nothing about the data changed; only the table of critical values did. The Engle-Granger p-value of 0.2255 is far above the 0.05 threshold, so cointegration_passed is 0.

Trap: a high R-squared is not evidence of cointegration

This is the single most important idea in the project. The line explains 96.0 percent of the KO price variation, which looks conclusive and is worthless on its own. Two series that both drift upwards over twenty years will fit each other well by construction, a pattern known as a spurious regression. The only thing that matters is whether the leftover gap comes back, and the correct test says it does not.

Why both tests are reported when only one counts

The plain Dickey-Fuller p-value of 0.087 is the number a careless version of this study would quote, and at a 10 percent threshold it would look almost passable. Keeping it beside the correct 0.225 makes the size of the correction visible. The docstring is explicit that the Engle-Granger value is the gate and the other is a diagnostic.

The fit is a single fixed line, and it is never refreshed

fit_cointegration is called once, on data ending 2023-10-10, and the resulting $\hat\alpha$ and $\hat\beta$ are used unchanged for all 494 backtest days. That is the honest choice, because refitting inside the test window would leak information. But it also means that if the true relationship drifted during 2024, the strategy would keep trading a gap defined by a relationship that no longer exists. The blog/generate_charts.py diagnostic shows exactly that drift.

05The signal — compute_causal_signal

residual = prices["KO"] - fit.alpha_usd - fit.beta * prices["PEP"]
lagged = residual.shift(1)
rolling_mean = lagged.rolling(rolling_window).mean()
rolling_std = lagged.rolling(rolling_window).std(ddof=1)
return pd.DataFrame(
    {
        "residual_usd": residual,
        "rolling_mean_usd": rolling_mean,
        "rolling_std_usd": rolling_std,
        "z_score": (residual - rolling_mean) / rolling_std,
    },
    index=prices.index,
)
In plain words

Work out today's gap between the KO price and the line, then ask how unusual that gap is compared with the last sixty days of gaps — sixty days that stop yesterday, so today's gap is never allowed to help judge itself.

What it does

Input: the full price history, the frozen fit, and the window length. Output: a four-column frame on the same index as the prices: the gap, its trailing average, its trailing spread, and the score. Role: the z_score column is the only thing the trading rule looks at.

The formula — the score, exactly as the code builds it

$$\mu_{t-1}=\frac{1}{L}\sum_{i=1}^{L}e_{t-i}, \qquad \sigma_{t-1}=\sqrt{\frac{1}{L-1}\sum_{i=1}^{L}\bigl(e_{t-i}-\mu_{t-1}\bigr)^2}, \qquad z_t=\frac{e_t-\mu_{t-1}}{\sigma_{t-1}}$$

$e_t$ is today's gap in US dollars, from the previous section. $L=60$ is rolling_window. The sums run from $i=1$, not $i=0$: the window is $e_{t-60}$ through $e_{t-1}$ and stops one day short of today. The $L-1$ divisor is the sample standard deviation, which is what ddof=1 selects; ddof stands for delta degrees of freedom. $z_t$ is a pure number with no units: it says how many trailing standard deviations today's gap sits away from the trailing average.

One row checked by hand. On 2023-10-12 the gap is $e_t = 49.0459 - 4.573179 - 0.334505 \times 144.8800 = -3.9904$ US dollars. The 60-day window behind it runs from 2023-07-19 to 2023-10-11 inclusive, contains 60 values, and has average $-4.526974$ and spread $0.750488$. So $z_t = (-3.9904 - (-4.526974)) / 0.750488 = 0.71493$, which matches the 0.7149 the code reports. The window was printed separately and confirmed not to contain 2023-10-12 itself.

Why the shift comes before the rolling, not after

Two orderings look similar and one is wrong. The code writes residual.shift(1).rolling(60).mean(): shift first, then average. That gives the average of days $t-60$ through $t-1$. Writing residual.rolling(60).mean().shift(1) instead would give the average of days $t-61$ through $t-2$, a needless extra day of staleness. Writing plain residual.rolling(60).mean() would include today, which lets today's gap pull its own benchmark toward itself and shrinks every score.

Trap: the rolling window happily crosses the training boundary

On the first backtest day the sixty-day window sits almost entirely inside the training sample, where the gaps were fitted to average zero by construction. This is not look-ahead, because every one of those days is genuinely in the past. But it does mean the first few weeks of scores are normalised against a period the regression was tuned on, so they are slightly better behaved than a live trader would have seen.

The test that guards this

test_signal_does_not_use_current_or_future_residuals builds a twelve-day price frame, computes the signal, then adds 1,000 US dollars to the very last KO price and recomputes. It asserts every score except the last one is unchanged, and that even the last day's rolling average is unchanged. If anyone ever removed the shift(1), that test would fail immediately.

06Position sizing — _target_holdings

target_gross = config.initial_capital_usd * config.gross_exposure_multiple
ko_units = target_gross / (ko_price + abs(beta) * pep_price)
return side * ko_units, -side * beta * ko_units
In plain words

Choose how many KO shares to hold so that the two legs together add up to the target position size, then set the PEP shares to exactly the mirror image implied by the slope.

What it does

Input: today's two prices, the slope, a direction of +1 or -1, and the config. Output: two signed share counts. Role: called once per entry inside the backtest loop; nothing else calls it.

The formula — the sizing

$$q_t=\frac{C\cdot G}{P^{KO}_t+\lvert\hat\beta\rvert\,P^{PEP}_t}, \qquad n^{KO}_t=s_t\,q_t, \qquad n^{PEP}_t=-s_t\,\hat\beta\,q_t$$

$C$ is initial_capital_usd, 100,000 US dollars. $G$ is gross_exposure_multiple, 2.0. $P^{KO}_t$ and $P^{PEP}_t$ are the two closing prices on the entry day. $\hat\beta$ is the slope from the fit. $s_t$ is the direction: $+1$ to bet the gap widens back up, $-1$ to bet it narrows. $q_t$ is a positive share count. $n^{KO}_t$ and $n^{PEP}_t$ are the signed holdings, positive for owned and negative for shorted.

The denominator is chosen so the total position size lands exactly on target:

$$\lvert n^{KO}_t\rvert P^{KO}_t+\lvert n^{PEP}_t\rvert P^{PEP}_t =q_t\bigl(P^{KO}_t+\lvert\hat\beta\rvert P^{PEP}_t\bigr)=C\cdot G$$

in — first real entry, 2023-10-19 
ko_price   50.476109

                     total = 200000.0000  <- exactly C x G

The score was +1.5163, meaning the gap was unusually wide, so the code bet on it narrowing: side = -1, short KO and long PEP.

Why the absolute value appears in one place and not the other

The denominator uses abs(beta) because it is adding up position sizes, which are never negative. The PEP share count uses the signed beta because if the slope were negative the correct hedge would be to own both legs, not to short one. With the fitted slope of +0.3345 the two happen to agree, but the code stays correct if a different pair produced a negative slope.

This position is hedged on the relationship, not on dollars

At the first entry the KO leg is 101,256 US dollars and the PEP leg is 98,744 US dollars, so the position is close to dollar-neutral by coincidence, not by design. The slope of 0.3345 combined with a PEP price roughly three times the KO price is what makes the two legs come out similar. If the price ratio drifted, the position would carry a growing net exposure to the market as a whole, and the code would not notice.

07The backtest loop — run_backtest

This is the only complicated function in the project. It walks the 494 backtest days one at a time, carrying five pieces of state: the two share counts, the direction, the entry date, and the running trade totals. Each day happens in a fixed order.

flowchart TD A["mark prior holdings to today prices"] --> B["accrue borrow and financing on prior values"] B --> C["read today z-score"] C --> D{"holding a position"} D -->|yes| E{"z at the exit band, past the stop, or last day"} D -->|no| F{"z inside the entry band and not the last day"} E -->|yes| G["set both share counts to zero"] E -->|no| H["hold unchanged"] F -->|yes| I["size a new position at today's close"] F -->|no| H G --> J["charge cost on the change in holdings"] H --> J I --> J J --> K["update equity, record the row"]

Diamonds are decisions, boxes are actions. The order matters: profit and loss is settled before the signal is read, so a decision made today can never earn today's price move.

Step one — mark yesterday's position to today's prices

if previous_prices is not None:
    gross_pnl = ko_shares * (
        float(current_prices["KO"]) - float(previous_prices["KO"])
    ) + pep_shares * (
        float(current_prices["PEP"]) - float(previous_prices["PEP"])
    )
The formula — daily profit and loss

$$\Pi_t=n^{KO}_{t-1}\bigl(P^{KO}_t-P^{KO}_{t-1}\bigr) +n^{PEP}_{t-1}\bigl(P^{PEP}_t-P^{PEP}_{t-1}\bigr)$$

$\Pi_t$ is the day's gross profit or loss in US dollars, before any cost. $n^{KO}_{t-1}$ and $n^{PEP}_{t-1}$ are the share counts decided at yesterday's close, which are still what the variables hold at this point in the loop because they have not been updated yet. $P^{KO}_t$ and $P^{PEP}_t$ are today's closes. The subscript on the holdings is $t-1$ and on the prices is $t$; that mismatch is the whole timing discipline of the backtest.

Step two — charge the carrying costs

short_value = max(-ko_shares * float(previous_prices["KO"]), 0.0) + max(
    -pep_shares * float(previous_prices["PEP"]), 0.0
)
long_value = max(ko_shares * float(previous_prices["KO"]), 0.0) + max(
    pep_shares * float(previous_prices["PEP"]), 0.0
)
borrow_cost = short_value * config.short_borrow_rate_annual * daily_rate
financing_cost = long_value * config.financing_rate_annual * daily_rate
The formula — borrow, financing, and trading cost

$$B_t=\frac{r_b}{D}\Bigl[\max\bigl(-n^{KO}_{t-1}P^{KO}_{t-1},\,0\bigr) +\max\bigl(-n^{PEP}_{t-1}P^{PEP}_{t-1},\,0\bigr)\Bigr]$$

$$F_t=\frac{r_f}{D}\Bigl[\max\bigl(n^{KO}_{t-1}P^{KO}_{t-1},\,0\bigr) +\max\bigl(n^{PEP}_{t-1}P^{PEP}_{t-1},\,0\bigr)\Bigr]$$

$$K_t=\frac{c}{10^4}\Bigl[\bigl\lvert n^{KO}_t-n^{KO}_{t-1}\bigr\rvert P^{KO}_t +\bigl\lvert n^{PEP}_t-n^{PEP}_{t-1}\bigr\rvert P^{PEP}_t\Bigr]$$

$B_t$ is the short borrow fee, $F_t$ the long financing charge, $K_t$ the trading cost, all in US dollars for day $t$. $r_b=0.01$ and $r_f=0.05$ are the annual rates. $D=252$ is trading_days_per_year, so dividing by it turns an annual rate into one trading day's share. $c=5$ is transaction_cost_bps and $10^4$ converts basis points to a fraction. The max terms split the position into the part that is shorted and the part that is owned; each leg pays only the rate that applies to it. Note $B_t$ and $F_t$ use yesterday's prices and holdings, while $K_t$ uses today's prices and the change in holdings decided today.

The formula — the account

$$E_t=E_{t-1}+\Pi_t-B_t-F_t-K_t,\qquad E_0=C$$

$E_t$ is the marked account value in US dollars at the close of day $t$, and $C$ is the starting capital. Every open position is revalued every day, so a losing trade shows up in the drawdown while it is still open rather than only when it is finally closed.

Step three — the entry and exit rule

is_last_date = row_number == len(sample) - 1
if side != 0 and (
    abs(z_score) <= config.exit_z
    or abs(z_score) >= config.stop_z
    or is_last_date
):
    exit_reason = (
        "end of sample"
        if is_last_date
        else "mean reversion"
        if abs(z_score) <= config.exit_z
        else "stop loss"
    )
    ko_shares = 0.0
    pep_shares = 0.0
elif (
    side == 0
    and config.entry_z <= abs(z_score) < config.stop_z
    and not is_last_date
):
    side = -1 if z_score > 0.0 else 1
The formula — the rule, as written

Open a position when flat:

$$s_t=-\operatorname{sign}(z_t) \quad\text{if}\quad s_{t-1}=0 \;\text{ and }\; z_{\text{entry}}\le\lvert z_t\rvert<z_{\text{stop}} \;\text{ and }\; t\ne T_{\text{end}}$$

Close a position when holding one:

$$s_t=0 \quad\text{if}\quad s_{t-1}\ne 0 \;\text{ and }\;\bigl(\lvert z_t\rvert\le z_{\text{exit}} \;\text{ or }\;\lvert z_t\rvert\ge z_{\text{stop}} \;\text{ or }\; t=T_{\text{end}}\bigr)$$

$s_t$ is the direction held after the close of day $t$: $+1$, $-1$, or $0$ for flat. $z_t$ is the score. $z_{\text{entry}}=1.5$, $z_{\text{exit}}=0.2$ and $z_{\text{stop}}=2.5$ are the three configured thresholds. $T_{\text{end}}$ is the last backtest date. $\operatorname{sign}(z_t)$ is $+1$ when $z_t$ is positive: the minus sign in front of it is the bet that an unusually wide gap will narrow.

Why the entry band has an upper edge as well as a lower one

The condition is $1.5\le\lvert z_t\rvert<2.5$, not simply $\lvert z_t\rvert\ge 1.5$. A gap already past the stop level would otherwise be entered and then immediately stopped out the next day, paying two lots of trading cost for nothing. The same value, 2.5, is doing two jobs: it is the risk stop and the edge of the tradeable band.

Why the last day is treated specially in both branches

is_last_date forces any open position shut, so the reported profit and loss covers only closed positions and no value is left dangling. It also blocks a new entry, since a position opened on the final close would be opened and closed in the same instant while paying cost twice.

Trap: the trade ledger is derived, not maintained separately

The daily loop accumulates trade_gross_pnl, trade_cost and trade_net_pnl from the same daily numbers that build the equity curve, then flushes them into a trade row on the exit day. There is no second set of books that could drift out of line with the first. The test test_costs_reduce_daily_marked_equity asserts trades["net_pnl_usd"].sum() equals daily["net_pnl_usd"].sum(), so the two views must reconcile exactly.

Trap: holding_days counts calendar days, not trading days

Entry happens at the same close that produced the signal

The score on 2023-10-19 is built from that day's closing prices, and the position is sized using those same closing prices. In practice you would have to submit a market-on-close order before knowing the closing print, or trade the following open. The gross profit and loss timing is correct either way, but the entry price is a touch optimistic.

returns = daily["net_pnl_usd"] / daily["equity_usd"].shift(1).fillna(

    float(returns.mean() / return_std * np.sqrt(config.trading_days_per_year))
    if return_std
    else np.nan
)
The formula — return, Sharpe ratio, drawdown

$$r_t=\frac{\Pi_t-B_t-F_t-K_t}{E_{t-1}}, \qquad S=\frac{\bar r}{s_r}\sqrt{D}, \qquad DD_t=\frac{E_t}{\max\bigl(C,\;\max_{u\le t}E_u\bigr)}-1$$

$r_t$ is the day's return as a fraction of the account value at yesterday's close; on the first day the denominator falls back to the starting capital $C$. $\bar r$ is the average daily return and $s_r$ its sample standard deviation across the 494 days. $\sqrt{D}$ with $D=252$ turns a daily figure into a yearly one, because independent daily returns add up in variance, so their spread grows with the square root of the number of days. $S$ is the Sharpe ratio, a ratio of average return to its spread; it uses no risk-free rate, so the funding charge inside $F_t$ is doing that job instead. $DD_t$ is the drawdown, the fall from the highest account value seen so far, with the starting capital counted as the first peak so a strategy that never gets ahead still shows its full loss.

Why the peak is clipped at the starting capital

cummax().clip(lower=initial_capital) counts day zero as a peak. Without the clip, an account that fell on day one and never recovered would measure its drawdown from that already-reduced level and report a smaller loss than actually occurred. Here the reported maximum drawdown of 47.3 percent is measured from the full 100,000 US dollars.

The Sharpe ratio here is a description, not a decision tool

With 494 daily observations and one strategy, a Sharpe ratio of -1.77 says the losses were persistent rather than one bad week. It carries no information about a future period, and because the study already failed its statistical gate, no reader should treat it as a ranking of anything.

In plain words

Take every price strictly before the backtest starts, keep the most recent five thousand of them, fit the line on those and only those, then run the strategy on the full history so the rolling window has something to look back at.

Why this is where look-ahead would have crept in, and does not

These four lines are the whole separation between what the model knew and what it was tested on. prices.index < config.backtest_start is a strict comparison, so 2023-10-11 itself is excluded from training. .tail(5000) then takes the most recent five thousand of those, ending 2023-10-10. The resulting fit is passed into run_backtest as a frozen object and is never recomputed inside the loop. Note that run_backtest receives the full price history, not the training slice: that is deliberate, because the rolling window on the first backtest day needs sixty prior days. Those prior days are all in the past, so no future information enters.

Trap: the length check turns silent truncation into an error

.tail(5000) on a shorter history returns whatever exists, without complaint. The strategy would then quietly be fitted on, say, 800 days while the configuration still claimed 5,000. The equality check catches that. This is the only guard of its kind in the pipeline and it is the right place for it.

The three ways to run it

Installed command: uv run statarb-pipeline, declared in pyproject.toml as statarb_cointegration.cli:main. Script: uv run python scripts/run_pipeline.py, a six-line file that imports the same main. Library: from statarb_cointegration.pipeline import run_pipeline, which is what notebooks/demo.ipynb does in a single cell. All three take an optional --config path, and all three write the same three CSV files.

What lands on disk

outputs/tables/daily_backtest.csv, 494 rows and 12 columns of daily state. outputs/tables/trades.csv, 13 rows of completed trades. outputs/tables/summary.csv, 16 metric rows written by hand with an f-string rather than through pandas. The whole outputs/ folder is in .gitignore, so running the pipeline never dirties the repository.

The third estimate is fitted on the backtest period itself, which would be a serious error if it fed a trading decision. It does not. The fit handed to run_backtest on the line above comes only from training. The three estimates exist solely to be drawn as three bars on a chart showing that the relationship was unstable. They are presentation choices, so nothing computed depends on them, but changing backtest_start in the settings file would leave the "Prior 2 years" bar labelled wrongly.

16Honest limitations

The pair and the split date were chosen with the whole history visible

This is the structural bias the code cannot fix, and it should not be papered over. KO and PEP were selected as a pair, 5,000 training days were selected as a window, and 2023-10-11 was selected as the split, all by a person who could already see every price through 2025. Nothing inside the pipeline is capable of undoing that. The mitigating fact is the direction of the result: the study reports a failed test and a 46.2 percent loss, which is the opposite of what a favourably chosen sample produces. A selection bias that hurts your own conclusion is not much of a bias. But if this design were reused on a pair that did pass, the same choices would make that pass much less impressive than it looks, and the honest fix is a proper out-of-sample protocol: choose the pair and the window on one period, then test on a period you have not looked at.

One pair, one window, one strategy — no statistical power either way

Thirteen trades over 494 days cannot support any claim about the strategy's expected return. The Sharpe ratio of -1.77 and the win rate of 0.31 are descriptions of what happened, not estimates of anything. The one number in the whole study that carries real statistical weight is the Engle-Granger p-value of 0.2255, computed on 5,000 observations, and it says the premise fails.

Adjusted closes are not tradeable prices

Every price in the parquet is a split-adjusted and dividend-adjusted close. There is no bid, no ask, no size, and no intraday path. The 5 basis point trading cost is a stand-in for a spread that is not in the data at all. Market impact, the possibility that KO shares were not available to borrow, dividends owed on the shorted leg, and broker-specific margin terms are all absent. The README says this plainly and it remains true.

Entry is priced at the close that produced the signal

The score and the entry price come from the same closing print. A real trader would either commit to a market-on-close order before seeing that print, or trade the next open. The profit-and-loss timing is right, but the fill is optimistic by roughly one day of noise on each of the thirteen entries and thirteen exits.

The position is sized once and never rebalanced

Share counts are fixed at entry and held until exit. Trade 10 ran 118 calendar days, over which the position size drifted away from 200,000 US dollars as prices moved, and the hedge ratio drifted away from 0.3345 in dollar terms. A live implementation would rebalance, pay for it, and get a different answer.

The relationship is fitted once and assumed to hold for two years

The slope comes from data ending October 2023 and is applied unchanged through September 2025. blog/generate_charts.py exists partly to show the slope was not stable across periods. Refitting inside the test window would be look-ahead, so the code is right not to do it; but that means the strategy is knowingly trading a relationship that has already been shown to move.
